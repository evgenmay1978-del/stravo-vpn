# STRAVO 1.0.7: конкуренты и обычный VLESS

Дата: 21.09.2026. Исследование, не реализация. Сверены исходники release
`631c761` / docs HEAD `56a8a48` и официальные материалы INCY, HAPP, Hiddify, v2rayNG.
GitHub подтвердил Latest v1.0.7. Установленная версия владельца отдельно не проверена.
Через Exa рассмотрены 20 результатов четырёх поисковых направлений; дубликаты не
считаются независимыми подтверждениями. Возможности конкурентов — по документации,
а не по запуску на устройстве владельца. Серверы/подписки в сети не запрашивались.

## Обычный VLESS: что известно

- Владелец: «по-моему CDN работает, обычный VLESS нет»; затем явно подтвердил:
  «в инси и хапп работает обычный влесс». Успех CDN пока предварительный.
- Это повышает приоритет клиентской совместимости STRAVO, а не изменения сервера.
  Один URL у разных клиентов ещё не доказывает идентичность ответов подписки.
- Наш CDN тоже использует VLESS, но с другим транспортом/защитой. Сравнивать нужно
  варианты соединения целиком, а не «CDN против протокола VLESS».
- Свежего журнала неудачного обычного подключения нет. Конкретная причина текущего
  отказа НЕ установлена. Старую запись про REALITY из IMPLEMENTATION.md не выдавать
  за свежий диагноз; уже внесённый chrome fingerprint повторно «не исправлять».

## Установленные ограничения кода

1. `PanelSubscription.kt:47-57`: из каждого Xray JSON-конфига берётся первый
   поддержанный outbound; routing, DNS, balancers и другие настройки полного
   конфига не сохраняются. `SingBoxConfigBuilder.kt:415-503` создаёт свой каркас.
   У INCY полный конфиг хранится и передаётся Xray с ограниченными адаптациями:
   [Full Xray configs](https://docs.incy.cc/en/full-xray-config/).
2. `PanelSubscription.kt:110` читает REALITY `publicKey`, но не `password`.
   Новый параметр документирован [Project X](https://xtls.github.io/en/config/transports/reality.html)
   и показан в [REALITY README](https://github.com/XTLS/REALITY/blob/main/README.en.md).
   Если JSON содержит только `password`, при преобразовании теряется ключ.
   Это конкретный дефект совместимости, НЕ доказанная причина случая владельца:
   `SubscriptionAccountAccess.kt:79-88` для Maestro по умолчанию запрашивает
   `format=links`, когда формат явно не указан. Нельзя исправлять JSON и объявлять
   обычную ссылочную подписку рабочей без наблюдения.
3. `SingBoxConfigBuilder.kt:356-395`: SNI/pbk/sid/flow передаются выбранными полями,
   для REALITY fingerprint принудительно chrome. Это существовавшая совместимость,
   а не новое доказательство ошибки. Параметры реального неудачного узла неизвестны.
4. `StravoVpnService.kt:247`: Connected выставляется после старта ядра, без
   подтверждения запроса через выбранный сервер. Зелёная кнопка не доказывает соединение.
5. DNS сейчас фиксирован: UDP 8.8.8.8 для прямого разрешения и UDP 1.1.1.1 через
   прокси (`SingBoxConfigBuilder.kt:426-440`). Это ограничение, но не доказанная
   причина различия CDN/ordinary.

## Существенные отличия конкурентов

| Возможность | Документировано у конкурентов | STRAVO 1.0.7 |
|---|---|---|
| Автовыбор по задержке | [Hiddify](https://github.com/hiddify/hiddify-app/blob/main/README.md) | «Авто» выбирает первый узел, а не лучший по измерениям |
| Проверка соединения через прокси | [HAPP ping](https://www.happ.su/main/dev-docs/ping) различает ICMP/TCP/via Proxy | Есть метрики активного узла и диагностика; нет такого инструментария по всему списку |
| Правила сайтов, IP, GeoIP/GeoSite | [INCY routing](https://docs.incy.cc/en/routing/), [HAPP routing](https://www.happ.su/main/dev-docs/routing), [v2rayNG](https://github.com/2dust/v2rayNG) | Есть разделение по приложениям, но не пользовательские профили сайтов/IP/geo |
| DNS-профили и DoH | [INCY routing](https://docs.incy.cc/en/routing/) | Жёстко заданные UDP-резолверы; полноценного редактора нет |
| Полный Xray JSON | [INCY](https://docs.incy.cc/en/full-xray-config/) | Извлечение одного outbound и преобразование в sing-box вместо сохранения полного конфига |
| Настройки отдельной подписки | [HAPP](https://www.happ.su/main/dev-docs/routing) | Две группы ordinary/CDN, не полноценный менеджер множества источников каждого вида |
| Заголовки и интервал обновления | [INCY](https://docs.incy.cc/en/subscription-format/), [HAPP](https://www.happ.su/happ/dev-docs/app-management) | Название, описание, announce, трафик/срок есть; routing, provider links, заданный интервал не поддержаны |
| Другие протоколы | [INCY](https://docs.incy.cc/en/subscription-format/) и [Hiddify](https://github.com/hiddify/hiddify-app/blob/main/README.md) | Нет VMess/WireGuard/AmneziaWG/TUIC/SSH как полноценных путей подключения; набор каждого конкурента различается |

## Дополнительные пробелы и уже готовое

- Управление источниками: импорт ещё одной подписки того же вида заменяет узлы
  (`SubscriptionRepository.kt:56-64`); удаление в `StravoViewModel.kt:400` глобальное.
  Отдельного переименования, отключения и редактирования источника в UI нет.
- Автоподключение/запуск при загрузке: старые поля `autoConnect/startOnBoot`
  только сохраняются (`SettingsRepository.kt:19-20,55-56`), потребителей нет;
  boot receiver в manifest отсутствует. Не путать это с рабочим системным
  переходом к настройкам уведомлений — `SettingsRows.kt:40-65` действительно открывает Android Settings.
- Фоновое расписание обновления отсутствует: обновление при запуске после устаревания
  данных и ручное обновление на телефоне уже есть
  (`StravoViewModel.kt:197,241`, порог 6 часов в `SubscriptionRepository.kt:233`).
- TV: есть управление VPN, выбор локации и приложений, обычная подписка и ручная
  диагностика сети. Однако нет телефонного поиска/фильтра/пинга в списке локаций,
  ручного обновления подписок и копирования/экспорта журнала
  (`TvLocationsScreen.kt:45`, `TvSettingsScreen.kt:49`, `MobileRoot.kt:174`).
  Отсутствие CDN на TV — согласованная граница продукта, НЕ недостаток.
- Резервная копия/экспорт конфигураций и редактор профиля не реализованы.
  Android backup отключён; «Поделиться» отправляет информацию о сервисе
  (`AndroidManifest.xml:43`, `ProfileScreen.kt:64`, `ProfileRepository.kt:11`).
  Добавлять экспорт следует только с отдельным решением о защите секретов.
- Уже реализованы: один Android/TV APK, отдельные ordinary/CDN источники,
  раздельный туннель с системными приложениями, переподключение при смене узла,
  импорт ссылок/логина/буфера/QR на телефоне, метаданные подписки, метрики активного
  узла, ручная диагностика и экспорт журнала на телефоне. Наличие в коде не
  подменяет наблюдение работы на физическом устройстве.

Наличие правила per-app — не то же самое, что правило для сайта. Умение прочитать
JSON — не то же самое, что исполнить весь конфиг. Работающая сборка — не сетевое подтверждение.

## Приоритет

1. P0: установить причину обычного VLESS по журналу именно этого отказа и формату
   импорта; сверить перенос REALITY/Vision и фактическую версию встроенного ядра.
   Не трогать сервер, не повторять включение VPN на телефоне владельца без разрешения.
2. P1: честный статус доступности, автоматический выбор рабочего узла, эффективные
   настройки и самостоятельное управление каждой подпиской.
3. P2: DNS/доменные правила и дополнительные протоколы по реальной потребности.
   Не переписывать ядро и не копировать всё из конкурентов только ради равенства списков.

Существующий карандашный интерфейс, разделение ordinary/CDN и запрет CDN на TV
сохраняются. В этой работе исходники приложения, CI, релизы и серверы не менялись.
